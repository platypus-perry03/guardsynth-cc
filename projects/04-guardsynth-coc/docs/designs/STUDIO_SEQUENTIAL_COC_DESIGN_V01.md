## 1. 사용자 흐름과 성공 조건

사용자는 판단 시점을 선택하고 **CoC → 제약 → EBLC → 검증 → CNL** 순서로 작업한다. 전체 영상의 앞 시점들을 먼저 채울 필요는 없다. 기본 입력은 CoC 문장과 제약 설명 검토이며, 새로운 일반 입력 폼이나 규칙 JSON 편집은 추가하지 않는다.

성공 조건은 다음과 같다.

1. 시점 11만 작성돼도 현재 조건 안에서 검사할 수 있다. 1–10의 미작성은 오류 목록으로 반복 출력하지 않는다.
2. 이전 시점에 검토된 제약이 있으면 그 시점까지 축적한 상태를 이어받는다. 바로 전 시점의 후보 목록만 복사하지 않는다.
3. 시점 10이 나중에 작성되거나 수정·삭제·검토 철회되면 11과 영향받는 후속 시점의 기존 결과가 즉시 최신 표시에서 제외되고 자동 재계산된다.
4. 미작성, 검토 대기, 미관찰, 모순, 출처 미확인, 시스템 실패를 구별한다. 경고를 숨겨서 통과시키지 않는다.
5. 과거 입력 변경이 VLM 유료 재생성이나 작성자 승인 자동 실행으로 이어지지 않는다.
6. 현재 장면을 생성하는 VLM에는 현재·과거 프레임/CAN만 전달한다. 후속 관찰은 후속 시점의 조건 해제 검사에만 사용하며 과거 생성의 입력으로 되돌려 넣지 않는다.

### 접근 방식 비교

| 방식 | 장점 | 한계 | 결정 |
|---|---|---|---|
| 변경 시점부터 뒤의 작성 시점을 순서대로 재계산 | 누락·삭제·공백 연결 처리가 단순하고 보수적 | 실제 상태가 같아도 일부 후속 계산 반복 | **첫 구현 권장** |
| 의존 상태가 달라진 노드만 재계산하고 상태가 같아지면 중단 | 큰 영상에서 비용 감소 | 근거·정의 버전·공백·출처까지 비교하지 않으면 잘못 중단 | 성능 필요성이 확인된 뒤 확장 |
| 매번 전체 추출과 미작성 시점까지 검사 | 구현 단순 | 경고 과다, 부분 시작 불편 | 기존 방식, 새 흐름에는 사용하지 않음 |

범위는 기존 실행 한도인 추출당 최대 200시점, 시점당 16후보, 구간당 64조건으로 제한한다. 더 큰 범위를 조용히 자르지 않고 명시적으로 거부한다.

## 2. 시간 범위와 검증 노드

첫 버전의 자동 연결 범위는 **같은 video/extraction 안의 같은 검토 구간**이다. 다른 영상, 다른 추출, 명시적인 구간 경계 너머로 자동 연결하지 않는다. 단일 조건의 범위 종료는 전체 구간 경계가 아니다. 첫 버전은 추출 하나를 한 구간으로 취급하며 자동 장면 분할을 추가하지 않는다.

작성 상태와 검증 가능 범위를 분리한다.

| 작성 상태 | 의미 | 처리 |
|---|---|---|
| `UNWRITTEN` | CoC와 제약 작업 없음 | 시점 목록에 ‘미작성’. 개별 오류 검사 제외 |
| `DRAFT` | 일부 생성·수정 자료가 있지만 최신 검토 확인이 없음 | ‘검토 대기’. 기존 승인본이 있더라도 철회·수정된 상태를 무시하고 사용하지 않음 |
| `READY` | 현재 CoC·제약의 최신본이 검토 확인됨 | EBLC/검증 대상. 관찰 행동·근거가 일부 미확인이면 해당 검사의 범위만 제한 |
| `INPUT_INVALID` | 형식, 미래 근거, 명백한 참조 오류 | 구체적 입력 오류 표시. 잘못된 조건을 유효 조건처럼 전달하지 않음 |

제약 목록이 비어 있어도 **‘후보 없음으로 검토한 빈 목록’**과 **미작성**은 다르다. 전자는 새 조건을 만들지 않을 뿐, 이전의 유지 조건을 해제하지 않는다. 빈 목록으로 규칙 완전성을 주장하지 않는다.

관찰 행동 `[]`도 ‘아무 행동도 하지 않았음’이 아니다. `READY` 노드에서 관찰 행동을 확인하지 못했다면 규칙 간 검사는 하되 행동 비교는 `NOT_CHECKED`로 둔다. 화면은 ‘검토 필요’ 대신 ‘관찰 행동 값이 없어 행동 비교를 하지 못함’이라고 표시한다. 새로운 승인이 과거 원문 값을 자동 복구하지 않는다.

## 3. 이전 상태를 찾는 규칙

노드 `i`의 입력은 `local(i)`와 **바로 이전 추출 시점 `i-1`의 상태 요약**이다. 요약은 과거부터 유지된 조건의 최신 상태를 포함하지만 과거 프레임·CoC·SMT 공식 전체를 포함하지 않는다. 검증 창은 `i-1 → i`의 두 시점으로 고정한다. 이전 상태는 최신 검토 자료로 계산 가능한 상태이며 일관성 판정이 ‘모순 없음’일 필요는 없다. 모순 발견이나 행동 비교 미실행을 이유로 이미 관찰된 유지 조건을 버리지 않는다.

중간 미작성/검토 대기는 앞의 마지막 사용 가능 상태를 **검토 공백 표시와 함께 요약으로 전달**한다. 이것은 미작성 장면의 CoC·관찰을 생성하거나 검증 완료로 만드는 작업이 아니다. 예를 들어 9가 READY, 10이 미작성, 11이 READY면 10의 요약에는 ‘9에서 마지막 확인, 10 관찰 미확인’이 들어간다. 11의 SMT에는 10의 요약과 11만 넣는다. 9→11을 바로 인접 장면 검사로 취급하거나 9의 프레임을 세 번째 시점으로 추가하지 않는다. 이어받을 요약도 없으면 현재 시점에서 부분 시작한다.

| 이전 상태 | 현재 시점 처리 | 화면 표시 |
|---|---|---|
| 이전 사용 가능 노드 없음 | 알려진 정의 목록 없이 현재 후보에서 새 ledger 시작 | ‘여기서 시작 · 이전 조건 미연결’ |
| 바로 전 시점의 ledger 있음 | 이전 ledger + 현재 관찰로 상태 갱신 | ‘시점 10의 상태를 이어받음’ |
| 더 앞선 ledger는 있으나 중간 시점이 미작성/검토 대기 | 알려진 상태와 공백을 바로 이전 시점의 요약으로 전달. 이전 관찰은 미확인 | ‘마지막 확인 9 · 직전 10은 미작성’ |
| 이전 노드의 후보 목록은 비어 있지만 ledger에 유지 조건이 있음 | 빈 목록이 아니라 누적 ledger를 이어받음 | ‘이전부터 유지된 조건 2개’ |
| 이전 노드가 계산 실패/입력 오류 | 그 노드에서 확인한 것처럼 연결하지 않음. 더 앞선 사용 가능 상태를 전달하고 실패 구간 표시 | ‘이전 입력을 적용하지 못함 · 연속성 미확인’ |
| 이전 조건들이 근거 있게 해제됨 | 해제된 조건의 이력·정의는 남기고 활성 의무는 제거 | ‘유지 조건 없음 · 해제 이력 있음’ |

‘이전 미연결’은 물리적으로 과거에 제약이 없었다는 뜻이 아니다. 결과의 주장은 **현재 제공된 조건과 확인한 구간 안**으로 제한한다. 녹화 시작도 운전의 실제 시작이나 모든 위험의 종료로 간주하지 않는다.

구간 안의 첫 사용 가능 노드는 자동 기준점(anchor)이 된다. 더 이른 자료가 나중에 확정되면 기준점과 연결 관계를 다시 계산한다. 이 기준점은 검증 작업 편의용이며, 앞에서 발생한 조건을 무시해도 된다는 인증이 아니다.

## 4. 조건 정의·관찰·상태를 분리한다

조건마다 다음 세 층을 별도로 저장한다.

| 층 | 내용 | 변경 원칙 |
|---|---|---|
| 정의 | 안정 ID, 정의 버전, 제약 분류·관계 유형, 주체, 관련 객체/영역 참조, 대상 행동, FORBID/REQUIRE, 발동·유지·해제 기준, 규칙 참조 | 같은 ID·버전에서는 동일하게 재사용 |
| 시점별 관찰 | TRUE/FALSE/UNKNOWN/CONFLICT, 객체 연결 확인, 현재 관계·범위 확인, 프레임/CAN 근거, 관찰 시각, 관찰 설명 | 각 시점에서 갱신 |
| 누적 상태 | ACTIVE/RELEASED/UNKNOWN, 최근 확인 근거, 이전 상태의 출처, 공백, 충돌/대상 미확인 | 이전 상태 + 현재 관찰로 계산 |

‘바리케이드 구간이 끝나면 해제’는 정의이며 ‘현재 프레임에서는 끝났는지 확인할 수 없음’은 관찰 설명이다. 두 문장을 같은 해제 문자열에 넣지 않는다. 현재 모델 원문은 그대로 보존하고 구조화된 정의/관찰을 별도로 둔다.

새 장면의 VLM은 알려진 정의 ID·버전을 참조하고 관찰만 갱신한다. 실제로 다른 조건은 새 ID 또는 명시적인 정의 개정으로 제안한다. 시스템은 한국어 문자열의 유사성만으로 같은 조건이라고 병합하거나 자동 승인하지 않는다. 부분 시작으로 같은 조건에 서로 다른 ID가 붙었다면 ‘조건 연결 확인 필요’로 남긴다. 일치하는 대상·의미를 확인하기 전까지 두 조건을 조용히 합치거나 기존 조건을 삭제하지 않는다.

정의 문구만 편집하는 것과 행동·대상·해제 기준을 바꾸는 의미 개정을 구별한다. 의미 개정은 적용 시작 시점을 가진 새 버전이며 이전 정의에 대한 검토가 자동 승계되지 않는다. 과거 오류를 정정하는 경우는 정정한 원 시점부터 재계산한다. 현재의 문자열 차이 경고는 **‘정의 변경 확인 필요’**로 표시하며 그 자체를 SMT 행동 모순이라고 부르지 않는다.

### 제약 분류와 같은 대상의 연결

현재 구현에는 명시적인 제약 분류가 없다. 조건 ID와 정의 필드를 비교하는 방식이다. 이번 개정안은 **분류 → 구체적 대상 → 자차와의 관계 → 적용 범위 → 발동·해제 조건**을 구분한다. 장면 간에 이어받는 것은 ‘신호’나 ‘선행 차량’이라는 종류 전체가 아니라, 같은 대상·관계·범위에 연결된 개별 조건의 정의와 누적 상태다. 신호 색, 거리, 속도 같은 관찰값은 현재 시점에서 다시 확인하며 이전 값을 현재 관찰 사실로 복사하지 않는다.

분류만 붙이는 방식은 화면 정리에 도움이 되지만 차량 교체를 구별하지 못한다. 별도의 완전한 객체 추적 시스템을 먼저 만드는 방식은 최소 기능의 범위를 넘는다. 첫 버전은 아래의 분류와 구간 안의 객체/영역 참조를 사용하고, 불확실한 연결만 검토하는 방식을 채택한다. 신뢰할 수 있는 원본 객체 ID가 제공되면 활용하되 모든 영상에 있다고 가정하지 않는다.

상위 클래스는 정확히 **7개**이며, 기준은 ‘제약이 생기는 원인과 확인해야 하는 관계’다. 구체적 물체 종류만으로 결정하지 않는다. 출발·정지·주행 지속·진입·차로 변경은 별도의 행동 축으로 두며 분류마다 복제하지 않는다. 규칙 출처와 조건의 발동·유지·해제 상태 역시 별도의 축이다. 모든 장면에 모든 클래스의 제약을 만들지 않고 관련 후보만 표시한다. 클래스별 후보가 없다는 사실로 그 위험이 없거나 조건이 완전하다고 인증하지 않는다.

#### 7개 상위 클래스

아래의 클래스명은 논리 설계 명칭이며 아직 Python 상속 계층을 구현한 것이 아니다. 내부 분류 코드는 이전 분류 제안과 연결해 유지한다. 공통 계약을 쓰는 클래스별 조건 인스턴스로 설계하며, 클래스 이름만으로 행동 의무를 만들지 않는다.

| 상위 클래스 | 내부 코드 | 추상 정의 | 하위 유형 예시 | 장면 간 연결 단위 |
|---|---|---|---|---|
| **통행 제어 제약** `TrafficControlConstraint` | `TRAFFIC_CONTROL` | 신호·표지·통행 규칙이 특정 이동에 부과하는 조건 | 신호, 정지·양보 표지, 우선권 | 적용 신호/규칙 + 교차로·차로 + 진행 방향 |
| **차량 상호작용 제약** `VehicleInteractionConstraint` | `VEHICLE` | 자차와 다른 차량의 상대 위치·경로·이동 관계에 따른 조건 | 선행, 교차, 맞은편, 옆 차로, 자차를 추월, 자차의 추월 대상 | 차량 ID + 관계 + 충돌/이동 구간 |
| **보행자·자전거 상호작용 제약** `VulnerableUserConstraint` | `VULNERABLE_ROAD_USER` | 보행자·자전거 등의 이동과 자차 경로의 관계에 따른 조건 | 횡단, 횡단 대기, 경로 접근 | 대상 ID 또는 확인된 그룹 + 관련 이동 영역 |
| **주행 경로 제약** `RoadPathConstraint` | `ROAD_LAYOUT` | 도로·차로의 형상과 연결 구조가 자차 이동에 부과하는 조건 | 곡선, 합류, 차로 감소, 차로 경계, 정지선 위치 | 차로/도로 구간 + 해당 이동 |
| **공간 통행 제약** `SpatialAccessConstraint` | `WORKZONE_OBSTACLE` | 점유·차단·작업 영역 때문에 통행 공간이 제한되는 조건 | 공사 영역, 차단물, 통행로를 막는 정차 차량, 낙하물 | 장애물/영역 ID + 제한·허용 통행 공간 |
| **노면 상태 제약** `SurfaceConditionConstraint` | `ROAD_SURFACE` | 관찰된 노면 상태에 따라 해당 구간에서 검토할 주행 조건 | 젖음, 결빙 의심, 물 고임 | 노면 구간 ID + 해당 상태 술어 |
| **시야·확인 제약** `VisibilityConstraint` | `VISIBILITY` | 실제 주행 환경에서 필요한 영역을 확인하지 못하는 데 따른 조건 | 구조물·차량에 의한 가림, 안개·어둠에 따른 시야 저하 | 확인할 영역 + 가림/시야 제한 원인 |

‘분류 미확인’은 여덟 번째 클래스가 아니다. `class_id=null`, `classification_status=UNRESOLVED`로 기록한다. 분류를 제안했으면 `PROPOSED`, 해당 분류를 검토했으면 `CONFIRMED`로 둔다. 이 상태는 객체의 동일성 확인 상태 및 조건의 TRUE/FALSE와 독립적이다. 분류를 확인했다고 같은 차량임을 확인했거나 제약이 활성임을 확인한 것은 아니다. 분류 미확인만으로 이미 확인한 술어의 논리 검사를 전부 중단하지 않되, 클래스별 연결을 추정해서 채우지 않는다. 이전 제안의 `OTHER`는 새 클래스 체계에서 미분류 상태로 해석하며 원문 값은 보존한다.

#### 공통 제약 계약과 클래스별 역할

각 조건 인스턴스는 다음 공통 정보를 사용한다. 물체 유형, 현재 관계, 제한 행동을 하나의 클래스명에 압축하지 않는다.

| 공통 정보 | 의미 |
|---|---|
| 조건 ID·정의 버전 | 어떤 조건을 이어받는지 식별 |
| 상위 클래스·하위 유형·분류 검토 상태 | 제약 원인과 연결에 필요한 관계를 분류 |
| 주체·관련 객체/영역 참조 | 누구와 어느 장소에 관한 조건인지 식별 |
| 적용 범위와 행동 대상 | 어디까지 적용되며 어떤 대상으로의 행동을 제한하는지 구별 |
| 발동·유지·해제 기준과 행동 효과 | 무엇이 확인되면 활성/해제되고 어떤 행동 조건으로 연결되는지 정의 |
| 시점별 관찰·근거와 연결 확인 | 현재 값과 동일 대상 여부를 별도로 기록 |
| 누적 상태·이전 상태 출처·공백 | 현재 후보에서 생략돼도 이전 유지 조건을 추적 |
| 규칙·정책 출처 | 관찰에서 만들어진 후보와 근거 있는 행동 의무를 구별 |

상위 클래스는 비교할 대상과 필요한 근거의 종류를 정한다. 발동·해제 여부는 개별 정의와 시점별 근거로 계산한다. 예를 들어 차량 클래스 자체에 ‘화면에서 사라지면 해제’ 같은 일괄 규칙을 두지 않는다. 모든 클래스는 동일한 누적 상태 계약을 사용하고 최종 EBLC에서 함께 검사한다. 새로운 클래스별 검증기나 객체 추적 서비스를 먼저 만들지 않는다.

#### 단계 2에서 entity·관계·행동 조건을 구체화한다

단계 2의 산출물은 제약 문장과 함께 **객체/영역 참조, 방향 있는 관계, 근거 있는 조건, 행동 효과**를 가진다. VLM이 기존 제약 생성 호출에서 함께 제안하고 작성자는 같은 화면에서 수용·수정한다. 단계나 유료 모델 호출을 추가하지 않는다. 첫 버전은 구간 안의 참조 목록을 기존 revision 자료에 저장하며 별도의 범용 지식 그래프 서비스는 만들지 않는다.

‘대상’은 다음 세 역할로 구분한다. 객체/영역 자체의 유형은 VEHICLE, PERSON, SIGNAL, LANE, ZONE 등의 관찰 유형이며, 상위 제약 클래스와 같은 분류가 아니다.

| 역할 | 논리 필드 | 교차 차량 예시 |
|---|---|---|
| 행동 주체 | `subject_ref` | 자차 `ego` |
| 조건의 원인 대상 | `condition_target_refs` | 교차 차량 `vehicle_A` |
| 제한 행동의 대상 | `action_target_ref` | 진입하려는 교차로 영역 `zone_Z1` |
| 적용 구간·이동 | `applicability_scope`, `movement_ref` | 교차로 Z1의 자차 직진 이동 M1 |

조건의 원인 대상과 행동 대상이 같을 수도 있지만 자동으로 같다고 두지 않는다. ‘차량 A 때문에 Z1에 진입하지 않음’은 ‘차량 A에 진입하지 않음’이 아니다. 프레임에서 식별할 수 없는 참조는 미확인 상태로 남기며 CAN 속도·조향만으로 다른 차량의 ID나 경로 관계를 확정하지 않는다.

관계는 `관계 주체 → 관계 유형 → 관계 상대`, 적용 영역/이동, 시점별 진리값·근거로 표현한다. 예를 들어 `vehicle_A → CROSSES_PATH_OF → ego`는 Z1/M1에서의 관계이며, `signal_S → CONTROLS_MOVEMENT → movement_M1`은 신호 S의 적용 방향을 표현한다. 객체 ID와 관계 정의는 연결 가능하게 유지하고 현재 관계가 성립하는지는 시점마다 다시 관찰한다. 관계 참조는 해당 관계의 정의·근거와 승인 revision을 추적한다.

| 관계 계열 | 예시 | 조건으로 만들 때 필요한 추가 확인 |
|---|---|---|
| 차량 상대 관계 | LEADS, ADJACENT_TO, CROSSES_PATH_OF, ONCOMING_TO, OVERTAKES | 같은 대상과 이동 구간, 상대 위치·경로·간격 등 개별 조건의 근거 |
| 통행 제어 적용 | CONTROLS_MOVEMENT, RULE_APPLIES_TO_MOVEMENT | 자차의 해당 이동에 실제 적용되는지, 현시·규칙 출처 |
| 공간 점유·위치 | OCCUPIES_ZONE, BLOCKS_PATH, LOCATED_IN | 어느 객체가 어느 영역을 점유/차단하며 어떤 이동과 관련되는지 |
| 시야·관찰 관계 | OCCLUDES_VIEW_OF, VISIBILITY_LIMITED_IN | 실제 가림인지, 확인할 영역이 무엇인지, 단순 영상 부족과의 구별 |
| 도로 연결·노면 적용 | CONNECTS_TO, MERGES_INTO, SURFACE_STATE_IN | 해당 차로/구간과 자차 이동의 연결, 노면 상태의 관찰 근거 |

방향을 뒤집으면 의미가 달라지는 관계는 인자를 보존한다. `A OVERTAKES ego`와 `ego OVERTAKES A`를 같은 관계로 합치지 않는다. 한 대상에 여러 관계가 동시에 성립할 수 있으므로 역할 하나를 전역적으로 강제하지 않는다. 위의 관계명은 Studio의 중간 표현 제안이며 모두 현재 EBLC의 내장 연산자라는 뜻은 아니다.

관계 자체는 행동 의무가 아니다. ‘A는 선행 차량’이라는 관계만으로 정지나 주행 지속을 요구하지 않는다. 개별 조건이 사용하는 근거 술어, 예를 들어 검토된 간격 기준 미충족 또는 충돌 영역 점유를 연결하고 그 조건의 규칙/정책 출처와 행동 효과를 보존한다. 정량 기준이 없으면 수치 안전성 검사로 승격하지 않는다. 서로의 경로가 기하학적으로 교차한다는 이유만으로 동시 충돌이나 진입 금지를 확정하지 않는다.

단계 3은 검토된 참조와 조건을 읽어 다음을 명시적으로 연결한다.

1. `subject_ref`, 조건 대상, 적용 영역은 지원되는 EBLC 프로파일의 subject/target/zone binding 또는 Studio Core 변환의 참조에 연결한다.
2. 관계와 상태는 근거·시점·정의가 있는 조건 술어에 연결한다. UNKNOWN과 CONFLICT를 FALSE로 강제하지 않는다. 미지원 관계/검사에는 ‘변환 지원 없음’을 표시하고 자연어를 임의의 확정 Boolean으로 대체하지 않는다.
3. 개별 조건의 발동·유지·해제는 누적 상태 계약으로 변환한다. 같은 객체라도 다른 이동·영역에 관한 조건을 합치지 않는다.
4. 행동은 `행동 주체 + 행동 유형 + 행동 대상 + 이동` 단위로 구분해 Core 변수에 연결한다. 원인 객체 ID를 행동 변수의 대상에 대신 넣지 않는다. 여러 조건이 같은 행동을 제한하면 **동일한 행동 변수**를 참조한다.
5. 참조·관계·조건 ID에서 생성된 EBLC/Core 절까지 변환 근거를 남긴다. 오류를 원래 제약 카드와 영상 근거로 되돌려 보여준다. 출처·관찰 미확인은 별도 결과 축에 유지한다.

기존 [EBLC action 계약 스키마](../../../../platforms/eblc-bcv/src/guard_synth_eblc/schemas/eblc_action_contract.schema.json)는 subject/zone와 obligation의 target/predicate를 표현하고, [EBLC program v0.2 스키마](../../../../platforms/eblc-bcv/src/guard_synth_eblc/schemas/eblc_program_v0_2.schema.json)는 target binding, predicate와 lifecycle을 표현한다. 둘은 각각 지원 범위가 제한된 프로파일이다. 7개 클래스의 모든 조건이나 임의의 관계 그래프가 이미 그대로 지원된다고 주장하지 않는다. 현재 Studio는 직접 Core를 생성하며 대상 없는 전역 행동 변수를 쓰므로, 이 개정안의 대상·이동별 변환은 후속 구현에서 추가해야 한다.

예를 들어 제약 C_A는 ‘A가 Z1의 해당 충돌 영역을 점유하는 동안 ego의 Z1/M1 진입 제한’으로 정의한다. 다음 시점에서 A의 동일성과 점유 해소가 확인되면 C_A를 해제할 수 있다. 신호 S의 녹색 관찰만으로 C_A를 해제하지 않는다. 같은 Z1/M1 진입에 다른 조건이 있다면 C_A가 해제돼도 그 행동이 자동 허용되거나 요구되는 것은 아니다. 같은 시점의 실제 진입 관찰도 Z1/M1 대상 연결이 확인돼야 비교한다.

#### 선행·후행 조건과 CoC의 설명 연결

여기서 선행·후행 조건은 선행/후행 차량의 역할이 아니라 **행동 전의 조건과 행동 후에 확인할 상태**다. 한 판단은 ‘이전 누적 조건 + 행동 직전 상태 → 이유와 행동 → 행동 후 상태’로 연결한다. CoC의 이유 문장, 규칙상 행동 가능 조건, 실제 상태 전이를 구별한다. 녹색 신호는 진입 가능성을 뒷받침할 수 있으나 진입을 반드시 유발하는 충분한 원인이나 명령으로 두지 않는다.

| 구성 요소 | 기록할 것 | 교차로 진입 예시 |
|---|---|---|
| `preconditions` | 행동·이동에 적용되는 검토된 선행 조건의 참조와 행동 전 근거 | 적용 신호 확인, 관련 충돌 영역의 확인, 이전 진입 제한의 유지/해제 여부 |
| `reason_claims` | CoC가 이유로 제시한 사실/관계 참조, 설명하는 행동, 근거 | ‘적용 신호가 녹색이고 확인한 충돌 조건이 해소되어 진입했다’ |
| `observed_action` | 행동 주체·유형·대상·이동과 시작/종료 시각 또는 가능한 시간 구간 | ego의 Z1/M1 진입 |
| `expected_postconditions` | 행동 이후 확인할 상태, 전이 의미, 확인 구간·기한이 있으면 그 출처 | 진입이 완료됐다는 주장이라면 ego가 해당 영역 안으로 이동했는지 |
| `observed_postconditions` | 후속 영상/CAN에서 실제 확인한 상태와 시각·근거 | ego의 위치/경로 상태. 속도만으로 영역 진입을 확정하지 않음 |
| `invariants` | 해당 행동/구간 동안 계속 유지돼야 하는 검토된 조건 | 작업 영역 진입 금지, 적용되는 충돌 제한 |
| `change_causes` | 변화한 상태에 연결된 자차 행동 또는 외부 사건과 근거 | 신호 현시 변경, 다른 차량의 이탈, 자차의 구간 통과 |
| `required_condition_refs` | 행동별로 확인할 조건 목록의 출처·버전과 적용 범위 | 검토된 교차로 진입 템플릿. 목록이 없으면 완전성 검사 범위 미확정 |

선행 조건과 예상 후행 조건은 VLM이 기존 CoC·제약 생성 안에서 제안하며 별도 유료 단계를 추가하지 않는다. 구조화된 문장 중 어느 행동을 설명하는지도 연결한다. 이후 EBLC/Core에서는 선행 조건과 확인된 행동을 비교하고 지원되는 전이 술어·불변 조건을 검사한다. 자연어 이유를 화살표로 연결한 것만으로 실제 원인이라고 확정하지 않는다.

후행 조건은 ‘예상’과 ‘관찰’을 분리한다. 진입 시작과 진입 완료도 다르다. 검토된 시간 구간/기한이 없으면 다음 썸네일 하나에 결과가 나타나지 않았다는 이유만으로 실패를 선언하지 않는다. 아직 행동이 진행 중이거나 후속 영상이 없으면 ‘후행 조건 확인 대기/근거 부족’으로 둔다. 외부 차량의 이동이나 신호 변화는 자차 행동의 효과로 자동 귀속하지 않는다.

이 표현은 [Hoare의 선행·후행 조건](https://www.cs.cmu.edu/~crary/819-f09/Hoare69.pdf)을 장면의 조건·행동·전이 계약에 적용하는 **설계상의 대응**이다. 프로그램의 검토된 의미와 달리 VLM의 장면 해석·전이 모델 자체는 후보다. 실제 인과 효과를 식별하려면 추가적인 인과 가정과 자료가 필요하므로 시간 순서·계약 일관성을 ‘실제 인과관계 증명’으로 표시하지 않는다. 이 구별은 [Pearl의 인과 추론 개요](https://www.cs.princeton.edu/courses/archive/fall09/cos597A/papers/Pearl2009.pdf)에 근거한다. 첫 버전의 범위는 **CoC 인과 설명의 근거·시간·전이 일관성 검토**다.

#### 추가 검증 의무

| 검사 | 검출할 문제 | 판정 범위 |
|---|---|---|
| 선행 조건 충족 | 조건이 FALSE인데 해당 행동을 수행했거나, UNKNOWN인데 충족했다고 설명함 | 검토된 선행 조건과 해당 행동 전 관찰 범위 |
| 이유의 근거·관련성 | 다른 신호/차량을 원인으로 연결, 이유 사실과 관찰 충돌, 행동과 무관한 배경만으로 정당화 | 이유 참조와 행동·대상·이동 연결. 관계가 존재한다는 것만으로 의무 성립 인증 없음 |
| 원인과 행동의 시간 순서 | 행동 후 관찰한 사실을 당시 판단 근거로 사용, 오래된 상태를 현재 근거로 사용 | 관찰 시각·자료 가용 시각·행동 시간 구간. 구간이 겹치면 순서 미확인 |
| 후행 조건·상태 전이 | CoC가 주장한 진입/정지 완료와 후속 위치·주행 상태가 맞지 않음 | 검토된 전이 의미와 확인 가능한 후속 구간. 수치 임계값/동역학 없이 물리 안전성 증명 없음 |
| 유지 조건 보존 | 이전 ACTIVE 조건이 해제 근거 없이 현재 EBLC·CNL에서 사라짐 | 이전 누적 ledger와 현재 결합 결과의 대조. 현재 후보 생략 자체는 정상일 수 있음 |
| 해제·변화의 근거 | 다른 신호의 변경으로 차량 조건 해제, 대상 미관찰로 해제, 설명 없는 조건 변경 | 같은 대상·범위의 관찰·외부 사건·정의 버전 연결 |
| 조건 결합·예외·우선순위 | 같은 행동에 상반 의무, 근거 없는 우선순위로 제한을 무시, 예외 조건 누락 | 승인된 예외/우선순위만 적용. 클래스의 고정 순위로 자동 해결하지 않음 |
| 상태·행동 유형의 연속성 | 이미 정지 중인데 새 정지 행동으로 설명, 출발·정지 유지·주행 지속을 혼동 | 검토된 상태/행동 정의와 영상·CAN의 시간 연결. 자료 해상도 부족은 미확인 |
| 필요한 조건의 누락 | 검토된 행동 템플릿의 적용 항목이 없거나 미확인인데 완전한 설명으로 표시 | 제공된 템플릿·규칙 목록 안의 누락만 검출. VLM이 스스로 만든 목록만으로 완전성 인증 없음 |
| 설명의 순환·독립 근거 | ‘진행했기 때문에 진행이 정당함’, 결과를 원인 증거로 재사용, 모델 문장끼리만 서로 지지 | 이유→행동 설명의 의존 추적. 모델 간 합의만으로 관찰/규칙 근거를 대신하지 않음 |

누락 검사는 두 층이다. **기록된 조건의 보존 누락**은 ledger/변환 대조로 검사한다. **처음부터 추출하지 않은 조건**은 외부의 검토된 규칙·행동별 필수 조건 목록에 대한 대조가 있어야 검사 범위를 정할 수 있다. 7개 클래스는 후보 탐색과 표시를 돕지만 클래스 목록 자체는 필수 조건의 완전한 명세가 아니다. 나중 장면에서 위험이 나타났다고 과거에도 관찰 가능했거나 당시 활성이라고 소급 확정하지 않는다.

검증은 항상 **바로 이전 장면과 현재 장면**만 대상으로 한다. `1–2`, `2–3`, `3–4` 각각을 독립된 작은 SMT 문제로 검사하고 미해제 조건·미완료 후행 확인은 직전 요약으로 전달한다. 예를 들어 1에서 시작한 행동이 3에서 끝나면 2에서 ‘완료 확인 대기’를 전달하고 2–3 검사에서 현재 관찰로 완료를 확인한다. 1–3 전체를 다시 펼친 문제를 만들지 않는다. 제어 명령을 자동 실행하거나 완료 기한을 임의로 생성하지 않는다. 지원되는 상태 전이를 요약으로 표현할 수 없으면 다중 장면 탐색으로 우회하지 않고 지원 범위를 명시한다.

#### 구체적 하위 유형과 유지·해제 근거

| 화면 분류 | 내부 분류 / 관계 | 이어받는 대상과 조건 | 유지·해제를 확인할 근거 예시 |
|---|---|---|---|
| 신호·통행 제어: 신호 | `TRAFFIC_CONTROL` / `SIGNAL` | 특정 신호 또는 신호군, 교차로, 적용 차로·진행 방향, 자차의 해당 이동에 대한 진입 조건 | 같은 적용 신호의 현시 변화 또는 해당 교차로 통과 확인. 다른 방향의 녹색 신호로 해제하지 않음 |
| 신호·통행 제어: 표지·우선권 | `TRAFFIC_CONTROL` / `SIGN`, `RIGHT_OF_WAY` | 특정 표지 또는 규칙과 그 적용 차로·이동·영역 | 해당 범위 통과·이동 종료 근거. 우선권 해석에는 원문 규칙 연결이 필요하며 분류만으로 정당성을 확정하지 않음 |
| 선행 차량 | `VEHICLE` / `LEAD` | 차량 A와 자차가 같은 진행 경로에서 앞뒤 관계에 있을 때의 간격·진입 조건 | 같은 차량의 경로·상대 위치와 조건 충족 여부. 차량 A가 선행 관계에서 벗어났다는 근거와 새 선행 차량 B를 구별 |
| 자차를 추월하는 차량 | `VEHICLE` / `OVERTAKING_EGO` | 차량 A가 자차 옆을 통과하는 관계와 충돌 경로에 대한 조건 | 옆 차로 위치, 겹침, 통과 완료·경로 분리 근거. 화면 밖으로 나간 것만으로 통과 완료를 확정하지 않음 |
| 자차의 추월 대상 | `VEHICLE` / `EGO_OVERTAKING_TARGET` | 자차가 추월 중인 차량 A와 해당 추월 구간의 조건 | 추월 관계·차로 이동·안전 간격 회복에 관한 근거. 자차를 추월하는 차량과 구별 |
| 교차·맞은편·옆 차로 차량 | `VEHICLE` / `CROSS_TRAFFIC`, `ONCOMING`, `ADJACENT`, `UNRESOLVED` | 개별 차량과 교차·합류 영역 또는 자차 경로의 관계 | 해당 차량의 충돌 영역 이탈, 경로 분리 또는 관계 종료 근거. 방향을 알 수 없으면 `UNRESOLVED` |
| 보행자·자전거 | `VULNERABLE_ROAD_USER` / 횡단·접근 등 | 개별 대상 또는 근거가 있는 관찰 그룹과 횡단보도·충돌 영역 | 해당 대상의 이탈과 관련 영역 확인. 한 사람의 이탈로 다른 사람의 조건까지 해제하지 않음 |
| 차로·도로 형상 | `ROAD_LAYOUT` / 현재 주행 경로 | 차로, 곡선, 합류 구간, 정지선 등과 자차 이동의 조건 | 차로 연결과 구간 통과·이동 종료 확인. 다른 차로에 같은 조건을 자동 적용하지 않음 |
| 공사·차단물·장애물 | `WORKZONE_OBSTACLE` / 통행·회피 영역 | 특정 장애물/공사 영역과 주행 허용 영역·금지 영역의 조건 | 장애물 통과, 구간 종료 또는 경로 분리 확인. 한 차단물을 지났다고 공사 구간 전체를 종료하지 않음 |
| 노면 상태 | `ROAD_SURFACE` / 젖음·결빙 의심·고임 등 | 관찰된 노면 구간과 그 상태에 관한 주행 조건 | 같은 노면 구간의 상태 변화 또는 구간 통과 근거. 젖어 보인다는 이유만으로 마찰계수·안전 속도를 임의 확정하지 않음 |
| 시야 제한·가림 | `VISIBILITY` / 확인할 영역 | 가림 영역과 아직 확인하지 못한 교차 차량·보행자 등의 조건 | 가림 해소와 필요한 영역의 관찰 근거. 보이지 않는 것을 ‘없음’으로 처리하지 않음 |

표의 유지·해제 예시는 관찰할 항목이며 법규나 제어 임계값을 자동 확정하는 규칙이 아니다. 거리·시간 임계값이 필요한 후보는 원본 규칙/정책 또는 검토된 정의에 값과 출처가 있어야 한다. 모델이 임의의 ‘안전 거리’를 정형 검증의 확정 기준으로 만들지 않는다.

큰 분류의 경계도 고정한다. 정지선의 위치·형상은 차로·도로 형상에, 신호나 표지에 따른 통행 조건은 신호·통행 제어에 둔다. 노면 위의 떨어진 물체는 장애물, 젖음·얼음 같은 표면 상태는 노면 상태에 둔다. 비·안개·어둠은 관찰된 시야 저하가 제약의 근거일 때 시야 제한으로 다루며 날씨 이름만으로 제어 조건을 확정하지 않는다. 비 때문에 노면과 시야 조건이 모두 생겼다면 두 조건의 근거·해제 기준을 각각 연결한다.

물체 유형과 제약 클래스는 별도다. 정차 차량도 차량 ID를 유지한다. 앞차와의 간격 관계에 관한 조건이면 차량 상호작용, 통행로를 막는 점유에 관한 조건이면 공간 통행으로 분류한다. 같은 물체에 서로 다른 조건이 있을 수 있지만 하나의 조건을 분류 수만큼 복제하지 않는다. 화면상 차량 역할이 바뀌어도 같은 조건의 분류를 무조건 바꾸지 않고 정의의 관계가 끝났는지 먼저 확인한다.

제공된 영상의 화각·화질이 부족한 경우는 시점별 `관찰 미확인`으로 둔다. 실제 주행 환경에서 운전 판단에 필요한 영역이 가려졌다는 근거가 있을 때 시야·확인 제약을 제안한다. 단순한 카메라 누락을 주행 중 진입 금지의 확정 근거로 변환하지 않는다. 두 경우 모두 다른 클래스의 활성 조건을 ‘대상이 안 보임’만으로 해제하지 않는다.

분류 표기만 잘못됐고 대상·관계·술어·변환 의미가 그대로라면 분류 주석 revision을 정정해 원문과 기존 의미 검토 이력을 보존한다. 같은 정의 ID·버전의 의미 필드를 덮어쓰지 않는다. 분류 정정이 실제 관계·적용 대상 또는 EBLC 변환을 바꾼다면 의미 개정으로 다루고 해당 내용은 재검토한다. 분류명은 조건의 의미를 대신하지 않는다.

차량의 물리적 ID와 역할은 다르다. 화면에서 선행·추월 차량을 나눠 보여주되 내부에서는 `VEHICLE`과 관계 유형을 조합한다. ‘차량 A가 선행 차량인 동안’이라는 정의의 관계 유형은 고정하고, 현재 A의 관계는 시점별 관찰에 기록한다. A가 옆 차로로 이동했다는 근거가 있으면 기존 선행 관계 조건을 재평가하고 필요한 옆 차로 조건을 별도로 제안한다. 기존 조건을 단순히 ‘옆 차로’로 이름 바꿔 같은 정의라고 취급하지 않는다. 관계 종료만으로 더 넓은 충돌 위험 조건까지 해제하지 않는다.

각 객체/영역 참조는 같은 구간 안에서 유지한다. VLM이 ‘같은 차 같다’고 제안한 연결은 `PROPOSED`, 확인 근거가 없으면 `UNKNOWN`, 신뢰 가능한 원본 참조 또는 작성자의 근거 검토로 확정된 연결은 `CONFIRMED`다. 모델의 확신 점수만으로 `CONFIRMED`로 승격하지 않는다. 가림 뒤 다시 나타난 차량을 색·차종 또는 같은 분류만으로 기존 차량에 붙이지 않는다. 연결 미확인은 기존 활성 조건을 해제하지 않으며, 그 조건을 현재의 다른 차량에 강제 적용해 행동 모순을 선언하지도 않는다.

이전 조건을 이어받는 순서는 다음과 같다.

1. 같은 구간의 누적 조건을 가져온다. 현재 프레임에서 보이지 않는 대상의 조건도 이력과 상태에 남긴다.
2. 분류·관계로 비교할 후보를 좁히고 객체/영역 참조, 정의 버전, 적용 범위와 행동 대상을 확인한다. 분류 일치는 검색 기준이며 동일성의 증명이 아니다.
3. 연결이 확인된 조건은 현재 관찰로 발동·유지·해제를 계산한다. 다른 차량·신호·영역이면 새 조건으로 다룬다. 연결 미확인은 상태 보존과 검토 진단으로 남긴다.
4. 분류별 상태를 합쳐 동일한 자차 행동·대상·시점에 대한 EBLC 검사를 수행한다. 분류마다 별도 검사를 끝내면 신호 조건과 교차 차량 조건의 결합을 놓칠 수 있으므로, 검사 자체는 함께 수행한다.

여러 대상이 관련된 조건은 주 분류 하나와 관련 참조 여러 개를 가진 하나의 조건 ID로 기록한다. 화면의 여러 분류에서 참조할 수 있지만 ledger에 복제해 서로 다른 상태로 갱신하지 않는다. 가능하면 신호, 교차 차량, 보행자의 독립적인 진입 제한은 각각의 조건으로 생성해 해제 근거를 분리한다. 실제 결합 조건이라면 AND/OR 구조를 보존하고, 분류를 위해 의미가 다른 독립 조건으로 임의 분해하지 않는다.

녹색 신호 관찰은 같은 신호의 적색에 따른 제한을 해제할 근거가 될 수 있지만, 교차 차량·보행자·시야 제한의 조건을 일괄 해제하지 않는다. 녹색이라는 이유만으로 `REQUIRE ENTER`를 만들지 않는다. 또한 ‘진입 제한’은 곧바로 `REQUIRE STOP`을 뜻하지 않는다. 조건이 제한하는 행동과 실제 녹화된 자차 행동을 구별한다.

### 진입 행동의 대상

`ENTER` 하나로 주행로 진입과 금지 작업 구역 진입을 함께 표현하지 않는다. 관찰 행동은 행동 유형과 대상 영역/객체를 연결하고, 제약도 같은 대상에 연결한다. Core의 행동 변수 역시 대상별로 구분한다.

조건이 적용되는 장소·기간(`applicability_scope`)과 실제 행동이 향하는 대상(`action_target`)은 서로 다른 정보다. 예를 들어 공사 구간 안에서 적용되는 규칙이 작업 영역으로의 진입을 금지할 수 있다. CoC의 `ENTER → 유도 주행로`와 제약의 `FORBID ENTER → 작업 영역`은 같은 공사 구간에 있어도 다른 행동 대상이다. 두 대상의 관계가 확인되지 않으면 동일 대상으로 강제 연결하지 않는다. 대상 연결은 문장 유사성이나 CAN 속도만으로 확정하지 않고 근거와 검토 상태를 보존한다.

현재 장면에 대한 대상 연결이 없는 `ENTER`는 `TARGET_UNKNOWN`으로 남긴다. 해당 금지 영역에 들어갔다고 추정해서 행동 모순을 선언하지 않는다. `CONTINUE`도 주체와 적용 범위를 명시한다. 원문 문장을 바꿨다고 정형 행동이 자동으로 수정됐다고 간주하지 않는다.

## 5. 상태 전달과 불확실성

| 이전 상태 | 현재 관찰 | 다음 상태와 결과 |
|---|---|---|
| UNKNOWN/RELEASED | TRUE + 유효 근거 + 적용 범위 확인 | ACTIVE |
| ACTIVE | TRUE + 유효 근거 | ACTIVE, 최근 확인 갱신 |
| ACTIVE | 해당 조건 생략, UNKNOWN, 근거 부족 | ACTIVE 유지, 현재 관찰 미확인 표시 |
| UNKNOWN | 생략 또는 UNKNOWN | UNKNOWN 유지 |
| ACTIVE/UNKNOWN | FALSE + 조건 해소 근거 + 같은 적용 범위 | RELEASED, 재발동 관찰 대상은 유지 |
| 어느 상태든 | 근거 있는 범위 종료 ENDED | 해당 범위의 조건 종료, 정의·종료 이력 보존 |
| 어느 상태든 | CONFLICT | 기존 의무를 해제하지 않고 근거 충돌 기록 |
| RELEASED | 다시 TRUE + 근거 | ACTIVE 재발동 |

중간 시점이 빠져도 ACTIVE를 FALSE로 바꾸지 않는다. 공백 중 위험이 사라졌다가 다시 생겼을 가능성을 ‘없음’으로 처리하지 않는다. 반대로 처음부터 UNKNOWN인 후보를 새 근거 없이 ACTIVE 확정 사실로 승격하지 않는다.

종료된 조건을 기록에서 완전히 지우지 않는다. 정의 일관성, 재발동, 출처 추적에 필요한 이력을 유지한다. 한 조건의 종료가 다른 범위 조건이나 나머지 ledger를 초기화하지 않는다. 구간 끝의 잔여 조건은 ‘남은 조건’이며 종료 시점 위반으로 단정하지 않는다.

중간 미작성/검토 대기는 시점 간 관찰 공백으로 기록한다. 시간 간격이 큰 경우도 별도 공백 사유를 남긴다. 현재 제공된 연속 프레임이 일부 공백을 설명할 수는 있으나 자동으로 빠진 시점의 모든 상태를 확인한 것으로 취급하지 않는다.

## 6. 검증 결과는 독립된 축으로 표시한다

단일 `PASS/REVIEW_REQUIRED`로 모든 이유를 묶지 않는다.

| 축 | 예시 상태 | 의미 |
|---|---|---|
| 작성·입력 | 미작성 / 검토 대기 / 입력 오류 / 검사 가능 | 왜 이 시점이 검사됐는지 또는 제외됐는지 |
| 조건 간 일관성 | 알려진 조건 안에서 모순 없음 / 모순 / 결정 불가 / 미실행 | EBLC와 SMT가 검사한 범위 |
| 행동 비교 | 확인된 행동과 일치 / 행동 모순 / 관찰·대상 미확인 / 미실행 | 실제로 비교 가능한 행동 여부 |
| 연속성 | 여기서 시작 / 이전 상태 연결 / 관찰 공백 / 재연결 대기 | 검사에 반영한 시간 범위와 이력 |
| 규칙 출처 | 연결됨 / 미검토 / 미연결 / 해당 없음이 확인됨 | 법규·정책 원문과의 연결 상태 |
| 결과 최신성 | 최신 / 재검증 대기 / 실행 중 / 이전 결과 / 실패 | 현재 입력에 적용 가능한 결과 여부 |

대표 문장은 ‘알려진 조건 안에서 모순 없음 · 이전 조건 미연결 · 규칙 출처 미확인’처럼 조합한다. 출처 미연결이어도 조건 간 모순 검사는 수행한다. 그렇다고 법규 정당성, 조건 완전성, 안전성 또는 학습 적합성을 통과로 표시하지 않는다.

관찰 목록에 없는 행동은 자동으로 FALSE가 아니다. 확인된 양성·음성 관찰만 행동 질의에 넣고 나머지는 미정으로 둔다. 필수 행동이 미관찰인 경우 SMT SAT만으로 실제 수행이 확인됐다고 말하지 않는다. 규칙끼리의 질의와 확인된 행동 비교 질의는 분리한다.

조건의 적용 여부·대상·근거가 미확인이면 SMT가 가능한 해를 찾더라도 그 불확실성은 별도 축에 남긴다. 원문 출처 미연결뿐 아니라 관찰 불확실성도 완전한 검증 통과로 승격하지 않는다.

모델이 만든 후보에서 `REQUIRE CONTINUE`가 나와도 ‘현재 진행 중’이라는 관찰만으로 의무의 정당성을 확정하지 않는다. 외부 규칙이 없으면 후보·출처 미확인임을 보존한다. 규칙 목록이 있으면 그 목록에 대한 누락 가능성만 검사하고 목록 자체의 완전성을 인증하지 않는다.

### 타당성·실행 비용과 1차 검증 범위

앞 절의 추가 검증 의무는 확장 후보 목록이다. 모든 항목을 첫 버전의 필수 통과 조건으로 삼지 않는다. 성질마다 적용 조건, 기대 결과, 독립 근거, 반례 형태, 미확인 처리와 비용 한도를 먼저 정한다. ‘안전한 모든 행동을 증명’하는 문제와 ‘녹화된 특정 행동 설명의 모순을 찾음’은 서로 다른 검증 과제다. 이 Studio의 첫 버전은 후자를 대상으로 한다.

| 성질 | 타당하게 주장할 수 있는 범위 | 구현 방법·비용 성격 | 1차 결정 |
|---|---|---|---|
| entity·관계·행동 대상 연결 | 제공된 참조·방향·영역·이동의 구조적 일관성 | ID/타입/시각 비교. SMT 불필요 | 기본 검사 |
| 이전 조건 보존 | 알려진 ACTIVE 조건이 해제/범위 종료 없이 변환 결과에서 빠졌는지 | ledger와 EBLC/CNL 참조 집합 비교. SMT 불필요 | 기본 검사 |
| 해제·변화 근거 | 같은 대상·범위의 조건에 근거와 정의가 맞는지 | 이벤트·참조·근거 비교. 실제 위험 소멸 여부는 관찰 품질에 의존 | 기본 검사 |
| 조건 결합·행동 비교 | 선언된 조건과 비교 가능한 실제 행동의 일관성 | 유한 Bool/Enum 위주의 SMT. 모든 가능한 주행 경로 탐색 안 함 | 기본 검사, 자원 제한 |
| 선행 조건·시간 순서 | 선택한 행동의 검토된 선행 조건과 당시 관찰의 충족/충돌 | 주어진 값·시간 구간 비교, 필요 시 위 SMT 질의와 결합 | 기본 검사, 적용 조건 있는 항목만 |
| 후행 조건 | 정해진 전이 의미와 확인 가능한 현재 관찰의 일치 | 직전 요약의 미완료 기대 상태와 현재 관찰 비교. SMT에는 두 시점만 사용 | 조건부 검사. 미완료는 다음 요약으로 전달 |
| 필요한 조건 누락 | 제공된 검토 목록 안의 빠진 항목 | 참조 집합/적용 조건 비교. 열린 세계의 모든 위험 열거 안 함 | 목록이 있을 때만 진단 |
| 실제 인과 효과·필요/충분 원인 | 녹화와 모델 문장만으로 식별 범위 확정 불가 | 추가 인과 가정·대조 자료/실험 필요 | 첫 버전 제외 |
| 임의 길이 진행 보장·실수 동역학 안전성 | 목표·외부 환경·전이·시간/물리 명세 없이는 정당화 불가 | 무제한 시간 탐색·비선형 모델은 현행 프로파일 범위 밖 | 첫 버전 제외 |

두 시점의 검증 창은 계산 범위이며 완료 기한이 아니다. 세 번째 이후에 결과가 나타났다고 실패로 판정하지 않는다. 현재까지 확인하지 못한 후행 상태는 직전 요약에 남기고 다음 인접 쌍에서 갱신한다. 미완료 확인은 행동 ID·기대 상태·시작 시각·명시된 기한·근거 참조만 유지한다. 긴 검토 구간을 명시해도 SMT 시간축을 늘리지 않으며 지원되지 않는 장기 속성은 검사 미지원으로 남긴다.

**미확인 ≠ 위반, 모순 없음 ≠ 안전 인증**을 결과 정책으로 적용한다. 조건이 현재 후보에서 빠졌더라도 누적 상태가 보존됐으면 누락 오류가 아니다. 원본 규칙·영상·조건 적용이 확인되지 않은 항목은 근거 부족으로 표시하며 다른 검사 실행을 막지 않는다. 하나의 미확인 때문에 전체 CNL 작성이 영구적으로 막히지 않게 해당 범위와 미확인을 문장에 보존한다.

이전 ACTIVE 상태를 보존하는 것과 현재 위험 사실이 TRUE임을 확정하는 것은 다르다. 현재 관찰이 UNKNOWN이면 마지막 확인 시각과 불확실성을 함께 유지한다. 그런 가정에서 SMT가 UNSAT를 반환할 수는 있지만 ‘유지 계약 가정하의 충돌’과 ‘현재 확인된 입력의 모순’을 구별하고 실제 운전의 위반으로 확정하지 않는다. 근거를 잃었다는 이유로 ACTIVE를 자동 해제하거나 FALSE로 만들지도 않는다. 모든 모순 사례는 어떤 조건·출처·관찰 가정에 의존했는지 제시한다.

적용 신호·이동·행동 전 상태를 먼저 확인하고 실제로 적용되는 성질만 검사한다. 예를 들어 출발 검사를 주행 지속 장면에 일괄 적용하거나 녹색→진입 의무를 만들지 않는다. 상반 의무는 모델/규칙의 충돌일 수 있으며 작성자나 실제 운전의 잘못과 구별한다. 검사끼리 PASS를 서로의 전제로 쓰지 않고, 문장이 스스로 결론을 정당화하는 순환도 허용하지 않는다. 미확인 비율을 낮추기 위해 근거를 발명하거나 실제 조건을 삭제하지 않는다.

### 자원 예산과 성능 평가

대화형 인접 두 시점 검사 목표는 **통상 2초 이내**, 한 쌍의 벽시간 상한 제안은 **3초**다. 한 구간의 EBLC·검증·CNL 재계산 전체에는 **30초 벽시간 예산**을 제안한다. 시점마다 30초를 새로 부여하거나 청크마다 전체 예산을 초기화하지 않는다. 현재 작업은 이 두 시점 입력 계약과 3초 상한을 아직 구현하지 않았으며, 현행 CPU child는 단계별 30초 CPU/벽시간과 1GiB 주소 공간 한도를 사용한다. 목표와 현행 동작을 혼동하지 않는다.

SMT 입력은 직전 요약의 조건 정의 참조·상태·필요한 직전 관찰과 현재 장면의 검토된 조건·관찰이다. 요약의 지속 조건·미완료 기대 상태는 합계 64항목, 현재 후보는 16개로 제한하며 과거 이벤트 목록을 요약 안에 계속 추가하지 않는다. 원문·종료 이력은 저장소의 참조로 남기고 질의에는 필요한 상태만 펼친다. 한도를 넘으면 조용히 자르거나 조건을 버리지 않고 지원 범위 초과를 표시한다. 영상의 총 시점 수는 작업 수에 영향을 주지만 하나의 SMT 문제의 시간축을 늘리지 않는다. 두 시점으로 제한해도 질의 자체의 빠른 완료를 수학적으로 보장하는 것은 아니므로 벽시간 상한을 유지한다.

현행 `build_core`도 horizon=2의 상수 상태 모델을 생성하므로 30초 실측 초과가 과거 전체를 한 번에 펼친 시간축 때문이라고 주장하지 않는다. 현재 병목은 전체 시점 일괄 작업, 달라지는 상태마다의 상세 질의, 큰 결과의 반복 반환을 포함한다. 새 설계는 선택한 인접 쌍을 계산 단위로 하고 기본 질의·결과 반환을 줄이는 변경까지 포함한다. 두 장면 제한만으로 전체 재계산 비용이 자동으로 일정해지는 것은 아니다.

첫 버전은 기본 조건·행동 질의만 먼저 수행하고, 조건별 상세 SMT 진단은 충돌 발견 또는 사용자의 상세 요청 때 필요한 범위에 한정한다. 같은 입력·공식의 결과는 검토/근거/대상 revision과 함께 캐시하고 출처 매핑을 최신 자료에 맞춰 다시 연결한다. Boolean 공식이 같다는 이유만으로 다른 관찰을 같은 근거로 표시하지 않는다. 여러 시점의 동일 Core/SMT 전체를 결과 JSON에 반복 복제하지 않고 immutable 결과 참조와 시점별 요약을 사용한다.

구간의 기본 결과 응답은 **10MiB 이내**를 목표 한도로 제안한다. 전체 증명 자료는 개별 immutable artifact로 저장하고 필요한 시점만 조회한다. 한도를 맞추려고 조건·근거를 조용히 삭제하지 않는다. child peak RSS뿐 아니라 worker의 결과 읽기·저장 과정과 응답 크기도 측정한다. child의 1GiB 주소 공간 제한이 worker 메모리까지 제한한다고 주장하지 않는다.

timeout/메모리 초과는 ‘시스템/자원 한도로 검사 미완료’다. 논리 모순이나 안전 실패로 표시하지 않는다. 구간 예산 안에 처리한 범위와 남은 범위를 보여주고, 전체가 끝나지 않았다면 완료/전체 통과로 표시하지 않는다. 작업 취소·수정 합치기·재시작 복구를 유지하며 자동 유료 재생성이나 무한 재시도는 하지 않는다.

성능 판단은 정상 사례뿐 아니라 **캐시가 잘 되는 반복 상태와 시점마다 바뀌는 상태**를 나눠 측정한다. 현행 구현의 합성 입력 성능 실측은 [검증 성능 시험](../../artifacts/intermediate/guardsynth-studio-sequential-coc-001/studio-verification-feasibility-test-2026-10-03-001/REPORT_KO.md)에 기록한다. 새 entity/관계·선행/후행 스키마는 아직 구현되지 않았으므로 이 수치를 새 설계의 성능 보증으로 쓰지 않는다. 후속 구현은 정상/미확인/모순/상태 변경 입력에서 시간, child/worker 메모리, 결과 크기, 경고 이유를 함께 측정해야 한다.

## 7. 새 과거 자료가 생겼을 때의 무효화

자동 재검증은 한 번이라도 사용자가 검증을 요청한 시점에 대해 활성화한다. 아직 검증한 적 없는 장면의 검증 버튼을 자동으로 누른 것으로 취급하지 않는다. 다만 검증 대상의 이전 상태를 계산하기 위한 ledger 생산은 결정적으로 수행할 수 있다.

| 변경 사건 | 재계산 시작과 처리 |
|---|---|
| 이전 미작성 노드에 초안 저장 | 연결 대기·공백 가용 상태가 바뀌므로 해당 표시와 의존을 갱신. 초안은 확정 조건으로 전달하지 않음 |
| 이전 미작성 노드의 CoC·제약 검토 확정 | 새 노드부터 재연결. 그 이후 기존 검증 대상의 EBLC/검증/CNL 무효화 |
| 이전 제약·근거·대상·해제 정보 수정 | 수정 노드부터 후속 작성 노드 재계산 |
| 이전 조건의 분류·관계·객체 연결 정정 | 정정 노드부터 대상 연결과 후속 상태 재계산. 단순 표시 분류 정정은 정의 의미 변경과 구별하며 행동 모순으로 표시하지 않음 |
| 이전 후보 삭제·검토 철회·REJECT/HOLD | 즉시 현재본 사용 중단. 삭제/철회 노드부터 재계산하며 미확인 공백 표시 |
| 제약 없는 빈 목록으로 검토 | 이전 ledger를 지우지 않음. 새 입력 상태와 공백 정보를 반영 |
| 현재 CoC·관찰 행동 수정 | 현재 행동 비교 재계산. 제약 검토 의존이 무효화되면 검토 대기로 바꾸고 후속 공백 재계산 |
| 이전 CoC 문장만 수정 | 현행 검토 의존 규칙을 적용. 제약 검토가 무효화되면 재확정 전까지 사용하지 않음 |
| 규칙 원문·검토 상태 변경 | 해당 구간의 출처·누락 판단과 연결된 결과 재계산 |
| 영상 순서·프레임/CAN 연결·경계 변경 | 해당 구간의 시간 의존을 재작성. 이전 근거/승인과 맞지 않는 입력은 복구 전 제외 |
| 현재 시점의 후행 관찰 추가·수정·철회 | 해당 인접 쌍과 현재 출력 요약을 무효화하고 다음 쌍으로 재계산을 전파. 먼 과거 행동의 시작 시점까지 후속 관찰 의존을 소급 연결하지 않음 |
| 영상 권한 철회 | 새 생성과 결과 공개 중단. 이전 결과로 현재 유효 상태를 대신하지 않음 |
| 변환기·검증기·문장 생성 버전 변경 | 해당 단계와 후속 단계 무효화. 변경되지 않은 VLM 원문은 보존 |

첫 버전은 변경된 가장 이른 시점 `dirty_from`부터 구간 끝까지 요약을 시간순으로 다시 계산하고 기존 검사 요청 대상의 인접 쌍을 재검증한다. 미작성 노드는 관찰·SMT 검사 노드로 만들지 않으며 앞 상태와 공백의 요약 참조만 전달한다. 변경보다 앞선, 영향을 받지 않는 결과는 보존한다. 다른 video/extraction은 영향받지 않는다.

시점 k가 바뀌면 k-1→k 검사와 k의 출력 요약부터 재계산하고 k→k+1 이후로 전파한다. 예를 들어 11에서 시작한 행동을 12의 미완료 요약을 거쳐 13에서 확인했다면, 13 관찰 변경은 12→13 검사와 13 이후 요약에 반영한다. 11의 당시 판단 검사에 13을 추가하지 않는다. 현재 후행 확인 결과는 그 확인이 일어난 쌍에 저장하고 원 행동 ID로 추적한다. 모든 상태 전달은 순방향이며 과거 생성·당시 조건을 미래 관찰로 덮어쓰지 않는다.

‘제약이 없었음’도 의존성이다. 사용한 이전 노드 ID만 저장하면 기존에 비어 있던 시점의 새 제약을 놓치므로, 앞 구간의 작성·검토 가능 상태와 공백 서명도 결과 의존에 포함한다.

첫 버전은 전파 중간에서 계산 중단 최적화를 하지 않는다. 추후 중단하려면 ledger의 진리 상태뿐 아니라 정의 버전·대상 연결·근거·종료 이력·공백·출처·결과 범위가 모두 같아야 한다. 중단하더라도 이전 관계와 결과 최신성 의존 기록은 새 이력으로 갱신해야 한다.

## 8. 생성 맥락과 검증 의존을 분리한다

현재 구현의 `generation_context`는 앞 시점의 revisions를 묶고 그 값이 바뀌면 후속 제약 구성요소까지 stale로 만든다. 이를 그대로 두면 과거 작성 뒤 검증만 다시 하는 것이 아니라 후속 제약 재생성·재승인을 요구하는 순환이 생긴다.

새 설계에서는 다음을 구분한다.

- **생성 기록:** 모델이 실제로 본 과거 정의와 입력 서명. 변경하지 않고 보존한다.
- **로컬 검토 의존:** 같은 시점 CoC·제약·참조 정의 버전·원본 근거의 검토 유효성. 해당 내용 변경 시 재검토한다.
- **계산 의존:** 현재 결합한 이전 ledger와 앞 구간의 가용 상태. 과거 자료 변경 시 EBLC/검증/CNL을 다시 계산한다.

과거에 새 제약이 추가됐다는 이유만으로, 내용이 바뀌지 않은 현재 로컬 후보와 작성자의 검토 기록을 지우지 않는다. 새 과거 조건은 재계산에 추가한다. 현재 후보와 ID·대상·의미가 충돌하면 해당 연결을 ‘조정 필요’로 표시하고 기존 의미를 몰래 교체하지 않는다. 이 경우 조건 원문을 자동으로 고치거나 승인을 자동 승계하지 않는다.

과거 입력이 바뀌는 동안 **진행 중인 VLM 호출**은 예외다. 그 호출의 원래 입력과 현재 맥락이 달라졌다면 결과를 과거 맥락의 원문으로 보관하되 최신 후보로 적용하지 않는다. 자동 재호출하지 않는다. 이미 완료·검토된 로컬 후보의 보존과 진행 중 결과의 게시 규칙을 혼동하지 않는다.

선행 조건의 판단 시점과 후행 결과 확인 시점도 분리한다. 시점 11의 이유는 10→11 검사에서 당시 근거로 확인한다. 이후 완료 여부는 미완료 요약을 넘겨 11→12, 12→13에서 각각 갱신한다. 10→11 결과에 12·13 관찰 의존을 추가하지 않는다. 결과를 보고 당시 이유를 자동 수정하거나 승인하지 않는다. CNL의 후행 결과는 해당 인접 쌍에서 ‘이전에 시작한 행동의 완료를 현재 확인함’으로 구분하고 당시 조건과 혼합하지 않는다.

## 9. 실행, 저장과 동시 편집

새 테이블을 먼저 추가하지 않고 기존 immutable revisions, objects, receipts, CAS, Worker를 재사용한다. 아래는 논리 데이터 계약이며 구현 계획에서 정확한 스키마/API를 확정한다.

| 자료 | 필수 기록 |
|---|---|
| `condition_definition` | condition ID/version, 7개 중 class_id 또는 미분류 null, 하위 유형·정의의 관계 유형, 주체·관련 객체/영역 참조, 적용 범위, 행동 대상, 발동·유지·해제 술어와 출처. 분류 주석 revision·classification_status는 의미 변경과 구별 |
| `entity_binding` | 구간 내 객체/영역 ID, 원본 ID가 있으면 그 참조, 시점별 대응, PROPOSED/CONFIRMED/UNKNOWN, 확인 근거·검토 revision. 차량의 현재 역할은 객체 ID에 포함하지 않음 |
| `relation_binding` | 관계 ID, 방향 있는 인자 참조·관계 유형, 적용 영역/이동, 관계 정의·검토 revision. 시점별 관계 진리값·근거와 객체 동일성 확인을 분리 |
| `action_transition` | 행동 ID·대상·이동·시간 구간, preconditions/reason_claims, 예상 후행 조건, 불변 조건, 규칙/전이 정의·확인 구간 참조. 당시에 주장한 예상과 나중 관찰을 구별 |
| `transition_dependency` | 바로 이전 요약 ID/digest, 현재 시점 관찰 revision, 이전/현재 쌍 ID. 원 행동 시작 시점은 추적 참조이며 과거 장면 전체를 계산 입력으로 읽지 않음 |
| `condition_observation` | condition ID/version, 시점, 대상 연결 상태, 현재 관계·범위, TRUE/FALSE/UNKNOWN/CONFLICT, 관찰값과 근거. 신호 현시·차량 거리 등을 정의 ID에 포함하지 않음 |
| `node_input` | moment ID/ordinal/t0, CoC·제약 component ID와 검토 서명, 사용한 근거, 정의 버전, 작성 상태 |
| `node_dependency` | 구간 ID, 이전 ledger 노드/버전 또는 없음, 앞 구간 가용 상태 서명, 객체 연결·분류/관계 revision, 공백 목록, 원문 규칙 revision, 영상/CAN·도구 버전 |
| `node_output` | 들어온/나간 ledger, 미완료 후행 확인 참조, 지점 검사와 누적 검사, 각 결과 축, 조건별 진단과 근거. 후행 관찰은 원 시점 ledger 사실로 쓰지 않음 |
| `stage_artifact` | EBLC·검증·CNL 각각의 immutable 결과 ID, 부모 ID, 입력 digest, 실행 세대, 최신 여부 |
| `recompute_request` | 구간, 가장 이른 dirty_from, 요청 세대, 검사 요청한 노드 목록, 실행/실패 상태 |

가용 상태 서명은 이전에 실제 사용한 조건 목록뿐 아니라 **그 앞 시점들이 미작성·초안·검토 완료 중 무엇이었는지**를 포함한다. 의미 없는 UI 노출/스크롤 로그는 포함하지 않는다. 타임라인에 노드 삽입·삭제·순서 변경 시 관계를 재작성한다.

계산 순서는 다음과 같다.

1. 원본 수정·검토 이벤트와 영향을 받는 결과의 stale 표시를 같은 DB 트랜잭션으로 기록한다.
2. 같은 구간의 미실행 요청은 가장 작은 dirty_from으로 합친다. 새 입력은 요청 세대를 증가시킨다.
3. Worker가 현재 입력과 앞 상태 checkpoint를 잡고, 작성 노드를 시간순으로 재계산한다. checkpoint가 stale이면 더 앞선 유효 지점 또는 새 기준점으로 되돌아간다.
4. 기존 30초 CPU child·메모리 한도 안에서 필요한 이전 노드의 정의·관찰·ledger를 계산하고, 검증을 요청했던 대상에 대해 EBLC → SMT 검증을 수행한다. 검증 미요청 노드는 ledger 생산에만 쓰며 검증 완료로 표시하지 않는다. 이미 CNL을 요청했던 대상은 CNL도 갱신한다. 순서 전달은 predecessor outgoing 상태로 수행한다.
   - 각 SMT 문제는 바로 이전/현재 쌍만 소비한다. 미작성 시점은 상태/공백 요약만 전달하며 검증 완료로 표시하지 않는다. 과거 상태 복구가 필요하면 요약을 순차 재생하되 과거 장면들을 하나의 SMT 문제로 합치지 않는다. 검증 PASS는 상태 전달의 전제로 쓰지 않는다. 아직 확인 못한 후행 상태는 대기/근거 부족으로 요약에 남긴다.
5. 게시 직전에 입력 digest·권한·요청 세대·부모 결과·앞 구간 서명을 다시 비교한다. 모두 같은 경우에만 현재 결과 포인터를 갱신한다.
6. 오래된 작업은 이력으로 보관하되 최신 결과로 게시하지 않는다. 새 계산이 실패해도 오래된 결과를 최신으로 되돌리지 않는다.

두 사람이 동시에 수정하면 CAS 충돌 비교 흐름을 유지한다. 실행 중 여러 수정은 합쳐 새 입력으로 다시 계산한다. 프로세스 재시작 후 durable 요청을 복구하며, 동일 입력/단계 요청은 idempotent하게 처리한다. 승인 이벤트 자체는 재실행으로 새 승인 기록을 만들지 않는다.

기준점에서 뒤로 계산하는 순환은 만들지 않는다. ledger 계산은 source 자료만 소비하고 이전 검증의 PASS 여부를 승인 조건으로 소비하지 않는다. 규칙·행동 모순의 UNSAT를 다음 시점 전체의 논리 전제로 넘기지 않고, 조건 상태와 진단 이력만 전달해 이후 해제 장면을 독립적으로 검사한다.

## 10. 다섯 단계 화면과 CNL

기본 다섯 단계와 좌측 영상/CAN은 유지한다. 단계 4에는 다음만 기본 표시한다.

- 현재 시점의 구체적 검사 범위와 결과.
- ‘여기서 시작’ 또는 ‘어느 시점에서 이어받았는지’와 공백 여부.
- 현재 해결할 수 있는 항목에 대한 명확한 설명. 예: ‘관찰 행동 누락’, ‘신호 적용 방향 미확인’, ‘같은 조건 정의의 변경 확인’.
- 원문 출처 미연결은 한 번 요약하고 상세 정보에 둔다. 규칙 목록이 실제로 없다는 정보를 지우거나 확인된 법규처럼 표시하지 않는다.
- 이전 자료 변경 시 ‘시점 10의 제약이 추가되어 11–13을 다시 검사 중’과 완료 후 결과 변화.

전체 결과는 작성한 시점 중심 표로 보여준다. 미작성 시점은 개수와 공백 구간으로 요약한다. `9 → 11`은 인접 프레임 검사처럼 표기하지 않고 ‘10 미작성, 공백을 넘겨 이어받음’이라고 명시한다.

사용자가 최초 검증을 실행하면 뒤 세 단계의 자동 재계산 준비를 기록한다. 이후 이전 자료가 생기면 시스템이 자동 갱신한다. 작성자의 생성·수용·검토 행위는 자동 실행하지 않는다. 재검증 대기/실행 중에는 이전 결과를 접힌 이력으로만 제공한다.

CoC·제약의 관찰 행동 누락이나 대상 미확인처럼 기본 문장 수정만으로 해결할 수 없는 항목은 ‘현재 정보로 미확인 유지’, ‘명시적 재생성’, ‘근거를 확인한 뒤 해당 항목 수정’ 등의 작업을 해당 진단 카드에서만 제공한다. 원본 관찰 목록을 복구하려면 작성자가 선택해야 하며 시스템이 속도 수치만으로 행동을 채우지 않는다. 모든 장면에 추가 기술 입력을 요구하지 않는다.

단계 2의 제약 항목은 분류별로 묶고, 각 항목에 **‘분류 · 구체적 대상 · 제약 설명 · 이전 연결 · 현재 상태’**를 일정한 열로 보여준다. 예: ‘차량 / 선행 · 차량 A · 앞차와의 간격 조건 · 시점 10에서 이어받음 · 현재 간격 미확인’. 분류·관계·대상은 VLM이 함께 제안하고 작성자는 기존 수용 확인 또는 수정으로 검토한다. 모든 대상 ID·해제 술어를 사람이 직접 입력하게 하지 않는다. ‘신호’는 현시 관찰이고 ‘표지·우선권’은 표지/통행 규칙 근거이므로 설명만으로 구별이 안 되면 세부 분류 미확인으로 제안한다.

기본 표시에서 원인 대상 옆에 ‘자차와의 관계’, 제약 설명에 ‘제한 행동과 그 대상’을 읽기 쉬운 문장으로 함께 보여준다. 예: ‘차량 A · 자차 경로를 가로지름 · Z1 직진 진입 제한’. 수정은 대상·관계·행동 대상을 구별해 해당 항목에서 제공하고 기술 ID·관계 코드·규칙 JSON은 상세 정보에 둔다. 프레임/CAN 근거와 이전 연결 썸네일로 확인할 수 있게 하며, 관계명 선택만으로 발동 조건이나 출처가 확인된 것으로 처리하지 않는다.

같은 대상인지 불확실할 때만 해당 카드에 이전·현재 썸네일과 ‘같은 대상’, ‘다른 대상’, ‘확인 못함’을 제공한다. 근거 없이 첫 선택을 자동 승인하지 않는다. 단계 4는 분류별 **이어받음 / 새로 발견 / 해제 / 연결 미확인** 요약과 함께 결합 검사 결과를 보여준다. 분류 이름이나 색상이 논리 검사의 통과 표시가 되지 않는다. 기존 자료는 class_id 미분류 null과 대상 연결 미확인으로 읽고, 재분류만으로 유료 재생성하거나 과거 승인·원문을 덮어쓰지 않는다.

CNL은 최신 검증 입력과 같은 ledger에서 생성한다. 현재 후보뿐 아니라 이전부터 유지된 조건을 포함하고, 각 조건의 대상·미확인·출처 상태와 적용 범위를 보존한다. 발동 조건과 행동 결론을 분리해 ‘주행 지속인 경우 주행 지속을 요구한다’ 같은 중복을 피한다. 미확인 후보를 확정 명령문으로 승격하지 않는다. 모순이나 재검증 대기 상태를 함께 표시하며 최신 입력과 연결되지 않은 CNL은 현재 결과로 공개하지 않는다.

항상 `training_eligible=false`, `scene_truth_certified=false`, `rule_completeness_certified=false`를 유지한다. 이 설계는 인과 가설·조건 일관성 검토이며 사고 부재, 법규 적합성 또는 제어 안전성을 증명하지 않는다.

## 11. 구체적 시나리오

### A. 현재에서 시작한 뒤 이전 자료가 추가됨

| 사건 | 기준점/연결 | 기대 결과 |
|---|---|---|
| 11만 생성·검토 후 검사 | 11에서 시작 | 현재 조건 안에서 검사. 1–10 경고 반복 없음. 이전 미연결 표시 |
| 12 생성·검토 후 검사 | 11 → 12 | 11의 누적 상태로 12 검사 |
| 10 제약이 뒤늦게 검토 완료 | 10 → 11 → 12 | 11·12 결과 즉시 stale, 10 상태 계산 후 둘 다 재검증 |
| 10에 진입 금지가 활성이고 11에 해제 근거가 없음 | 금지가 11·12에 유지 | 같은 대상에 대한 확인된 진입이면 행동 모순; 대상/관찰 미확인이면 비교 미확인 |
| 11에 같은 대상의 해제 근거가 확인됨 | 11에서 RELEASED | 12에 해당 금지를 활성 상태로 강제하지 않음 |
| 이후 10의 검토 철회 | 10 사용 중단, 11 다시 기준점 가능 | 기존 연결 결과 무효화, 11·12 재계산, 미연결/검토 공백 표시 |

### B. 중간이 비어 있는 연결

9에 활성 조건이 있고 10이 미작성, 11이 작성됐다면 9의 상태를 10의 공백 요약으로 전달하고 10→11 쌍을 검사한다. 10이 없는 것을 해제로 처리하거나 10에서 새 관찰한 것으로 표시하지 않는다. 나중에 10의 근거 있는 FALSE가 확정되면 9→10 검사/요약을 갱신하고 10→11을 다시 검사한다. 11의 자체 근거가 다시 TRUE라면 11에서 재발동하며, 단순히 10에서 한 번 해제됐다고 이후를 영구 해제하지 않는다.

### C. 오래된 조건을 놓치기 쉬운 경우

7에서 발생한 조건을 8의 새 후보가 생략하고 9가 미작성이어도 10은 8의 **누적 ledger**를 이어받아 7의 조건을 검사한다. 8의 후보 목록만 전달하면 안 된다. 7의 정의가 삭제되거나 검토가 철회되면 8 이후 상태를 원 자료에서 재생해 제거/미확인을 반영한다.

### D. 신호가 바뀌어도 다른 분류의 조건이 남음

| 시점 | 현재 관찰 | 이어받은 조건 처리 |
|---|---|---|
| 1 | 자차 직진에 적용되는 신호 S가 적색, 교차 차량 A가 충돌 영역에 있음 | 신호 S에 따른 진입 제한과 차량 A에 따른 진입 제한을 별도 조건으로 활성화 |
| 2 | 같은 신호 S가 녹색으로 바뀜, A는 가려져 이탈 확인 불가 | 적색 제한은 근거와 정의에 따라 해제. A의 제한은 유지·관찰 미확인. 녹색으로 모든 제한을 해제하지 않음 |
| 3 | A의 충돌 영역 이탈 확인, 해당 영역에 새 차량 B 관찰 | A의 조건은 해제 가능. B는 같은 차량 분류여도 별도 대상·조건으로 검토 |

이 표는 진입을 요구하거나 급정지를 요구하는 정책이 아니다. 어떤 진입 제한이 유지되는지와 녹화된 행동이 비교 가능한지를 검사하는 예다. 시점 1이 뒤늦게 작성되면 2·3의 신호/차량 연결과 누적 조건을 다시 계산하되 기존 시점의 VLM 원문을 자동 재생성하지 않는다. 시점 2가 먼저 독립 작성되어 A에 다른 ID를 붙였다면 대상 연결 확인 전까지 자동 병합하지 않는다.

### E. 실제로 실행한 가상 두 장면 모델

[가상 시나리오 실행 결과](../../artifacts/intermediate/guardsynth-studio-sequential-coc-001/studio-pair-scenario-test-2026-10-03-002/REPORT_KO.md)는 적색 신호·교차 차량 때문에 대기하던 장면과 다음 판단 장면을 가정한다. 기존 EBLC 단일 zone action 프로파일을 Core로 변환해, 해제 확인 후 진입은 SAT, 교차 차량 점유가 확인된 상태의 진입은 UNSAT, 차량 이탈 미확인과 진입 보류는 SAT + REVIEW_REQUIRED로 구별했다. 현재 목록에서 차량 조건을 생략해도 이전 요약에서 이어받으면 충돌을 검출하며, 잘못된 모델이 해당 조건 자체를 지우면 SAT가 될 수 있으므로 구조적 보존 검사가 필요함도 확인했다. 진입 완료 주장과 후행 위치가 다른 사례도 UNSAT였다.

모든 예제의 기본 조건 모델은 SAT이고 관찰 행동·후행 상태를 별도 질의로 비교한다. 이는 제안한 성질의 작은 실행 예제이며, 새 Studio 스키마·증분 API·전체 클래스 체계를 구현하거나 실제 장면 인과/안전성을 증명한 결과가 아니다. 객체·적용 방향·정성 전이·규칙은 가상 입력에서 명시한 범위로 제한한다.

## 13. 구현 경계와 문서 후속 작업

프로젝트 전용 누적 검증 정책은 [studio_sequence.py](../../src/guard_synth/studio_sequence.py)에, 검토·의존·재계산 조정은 [앱 sequence.py](../../../../apps/guardsynth_studio/sequence.py)에 둔다. 재사용 가능한 Core/SMT 구현은 `platforms/eblc-bcv/`를 소비하며 프로젝트에 복제하지 않는다.

후속 구현에서 바뀌는 범위는 `generation_context`/freshness 분리, 제약 분류·관계·객체 연결과 대상별 행동 관찰 스키마, ledger와 입력/결과 축, Worker의 후속 재계산, 최소 UI 결과 표시다. 분류는 프로젝트 전용 생성·연결·표시에 사용하고 공유 EBLC/Core 플랫폼에 주행 분류 체계를 복제하지 않는다. 이전 API는 가능한 범위에서 호환하되 기존 전역 행동 자료를 대상이 확인된 자료로 자동 변환하지 않는다. 레거시 대상 없는 행동은 미확인으로 읽고 원본·승인 이력을 보존한다.

구현 전에 요구사항 8·9·11과 구현 계획을 이 개정안에 맞춰 갱신해야 한다. 연구 통제 계획, 법규 승인, 학습 적합성 규정은 이 문서로 바꾸지 않는다. 이번 산출물은 이 기존 설계 문서의 직접 개정이며 새 진행 로그나 중복 설계 문서를 프로젝트 docs에 추가하지 않는다.

## 2026-10-04 구현 연결 기준

실제 생성 실험의 immutable definition/current facts 및 closed entity/evidence binding을
프로젝트 소유 `studio_grounded_sequence.py`와 앱 provider/sequence에 연결한다.
새 생성은 바로 이전/현재 최대 2프레임과 같은 범위의 CAN만 보내며, 이전 정의와 상태 요약을 포함한다.
7프레임 영상 탐색 UI는 생성/검증 입력 범위와 구분한다. 기존 단순 후보는 호환 표시하며 구조화
정보가 없는 기록을 새 관계/대상으로 임의 변환하지 않는다.

입력 후보 → EBLC Core → Z3 검증 → 상태가 붙은 결정적 CNL을 별도 단계로 유지한다.
좌우/전후 관계와 대상별 행동 제약은 실제 Core 질의로 검사하고, 원문의 JSON pointer와 증거로 추적한다.
현재 인식 불확실·타입 오류·조건/대상 미연결·지원되지 않은 성질은 추가 확인으로 남긴다.
법적 출처 확인은 논리 모순과 별개다. CoC 자유 설명의 인과적 진실이나 장면 완전성을 인증하지 않는다.

원본 생성 성적은 생성 쌍과 검증기 버전에 묶어 최초 산출을 저장하며, 사람의 수정/승인으로
덮어쓰지 않는다. 새 세대 생성은 별도 평가 항목으로 남긴다. 수정본의 성적은 최신 검증 snapshot에
한해서 표시한다. 최초 원본이 없던 기존 수동 자료를 상용 모델 최초 통과율에 포함하지 않는다.
